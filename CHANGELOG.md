# Changelog

All notable changes to CatCup Tavern are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/). `0.1.0` records the M0 scaffold; `0.2.0` is the first early-access release; `0.2.1` is a compatibility patch; `0.3.0` is the M2 feature release; `0.3.1` adds profiles and book distillation; `0.3.2` asks providers for a request protocol, adds a first-class custom-provider entry and replaces every native dropdown with a CatCup control, and fixes the desktop console window, the Add-model button closing the Providers panel, and Sign out appearing with no password.

## Unreleased

### Added

- **A public landing page, in nine languages.** `site/` is a static page published to `gh-pages` by
  `.github/workflows/pages.yml`, with English at the root and `zh-CN`, `ja`, `ko`, `de`, `fr`, `es`,
  `ru` and `pt-BR` beside it, each with its own `<html lang>`, title, description, canonical and
  `hreflang` alternates. The page's one moving part is the product itself: a chat window built in HTML
  and CSS from the real components' structure and the app's own tokens, which accepts what you type and
  streams Mira's canned reply word by word, with Browser / LAN / Windows tabs that change only the
  window chrome around it. `scripts/build-site.mjs` renders the decks in `site/content/`, writes
  `sitemap.xml`, `robots.txt` and the assets, and fails when a locale is missing a key or leaves a
  placeholder behind; it has no dependencies and no bundler. `scripts/preview-site.mjs` serves the
  result on `:4173`, and `pnpm site` builds it. Every download button points at the installer asset
  itself (`releases/download/v<version>/CatCup.Tavern_<version>_x64-setup.exe`, named by the Tauri
  bundler and built from `package.json` at build time) rather than at the release page, and the install
  section names the file it downloads beside a link to every release.

- **An entry can answer to more than one name.** `公主` never fired on a chat saying `王女`, and the lexical pass cannot close that — it ranks shared words, it does not know two words mean the same thing. Each world info entry can now carry an **Also matches** list of extra names, edited as chips under its keywords, and the scanner treats every alias as an additional **primary** key: same matcher, same per-entry options, and the context inspector names the alias that fired. Because it is a primary key it is not merely additive — an alias also satisfies the secondary-key logic and shares inclusion groups, probability and the token budget, so a bad alias can hide an entry as well as reveal one, which is why the editor says so.

  Aliases are stored in **`<book>.aliases.json` beside the book**, never inside it. An entry's identity hash covers its whole raw record, `extensions` included, and a chat's `timedWorldInfo` records are matched by that hash — writing aliases into the entry would have silently detached its sticky and cooldown effects in every chat that already had them. Nothing in the book changes, so a book with no sidecar behaves exactly as it did, and the file moves, copies and is deleted with its book. They do not travel in a SillyTavern export; see `docs/LIMITATIONS.md`.

- **The model can propose those names.** **Generate aliases** in the book editor asks the active model about every entry — one request each, four at a time — and the sidecar is written only from a review sheet you accept. Each row starts at what the entry already carries plus what the model added, and a proposed name can be dropped without dropping the row, because unticking a row means "keep the old list" rather than "delete it". A proposal repeating one of the entry's own keys is filtered out before it is ever stored, as is anything too long to match a chat, and the list is capped at twelve per entry — a model asked for "other names" answers with thirty often enough that the cap is what stops an entry matching every scene. The dialog shows the request count and prompt tokens before it starts, counted with the same tokenizer the chat budget uses.

  **An import offers it.** The finished import dialog lists the books it just wrote with the request count each would spend, and one **Generate** button per book — because an alias set is worth most the moment a book arrives, and least three weeks later when the button has to be remembered. Nothing runs unless asked.

  Each generated set records the model that wrote it, shown beside **Also matches**. Nothing acts on it: it is there so a book filled in over several runs, possibly with a cheaper model for the bulk, can say which rows came from which — the difference between "these look wrong" and "the cheap model wrote these".

  **One command answers whether a book needs any of this.** `pnpm --filter @catcup/server recall <book.json> <chat.txt>` runs the real scanner over one paragraph three ways — the book's own keys, the same book with its alias sidecar, and that plus the lexical pass — and reports how many entries each reached. No provider, no cost, and it reads the app's own loader and scanner rather than reimplementing them. That is the measurement #127 said should decide whether an embedding layer is worth building.

  A run is **resumable**, which book distillation deliberately is not: records live in `<profile>/alias-runs/` and carry per-entry state, so a stop costs nothing already answered. A resume keeps a row's proposal only when the entry's content still hashes to what it was generated from, and leaves a row that was skipped (nothing to read) skipped unless the entry has since gained text. The book editor marks a generated set **Stale** once its entry has been edited and offers **Refresh** on that entry alone; a hand-typed list carries no provenance and is never stale, because a person wrote it against whatever the entry says today. A failed row says which kind of failure it was — the provider refused the request, or the reply could not be read — since the fix for one is not the fix for the other.

- **A lexical pass for world info.** Off by default, and switched on with `worldInfo.lexicalMatch`. A BM25F index over each entry's keywords, comment and content lets an entry fire on what the chat is _about_ rather than only on whether it repeats one of the author's substrings — so a chat mentioning the northern peaks can reach an entry keyed on "dragon" whose text describes where dragons roost. Nothing a keyword matched is removed, and inclusion groups, probability, the token budget, timed effects and the trigger and character filters all still apply; the pass only ever adds candidates, the same contract SillyTavern's Vector Storage keeps through `WORLDINFO_FORCE_ACTIVATE`. The inspector shows a lexical hit with its score and the reason `lexical`. `lexicalThreshold` (a fraction of the scan's best hit, because a BM25 score has no absolute meaning) and `lexicalLimit` bound the pass. Fields, documents and any other ST file are untouched: the setting lives in `settings.json`. The pass works from one shared chat window rather than a per-entry haystack, so an entry's own `scanDepth` and its `match*` opt-ins do not widen what it is matched against.

- **World info retrieval has settings you can reach.** The lexical pass, and the three values that bound it, were previously reachable only by editing `settings.json` by hand. Settings → World Info now ends with a collapsible **Retrieval** group: a checkbox for **Match by meaning, not only keywords**, a slider for **Entries per turn** (1–50), and **Trim weak matches** (0–100% of this turn's best hit). The group opens itself when the pass is already on. Two of the three controls are honest about what they can do: **Entries per turn** is a hard cap, so every step changes the turn's result, whereas **Trim weak matches** only ever trims the tail behind the best hit — the best hit is kept whatever the setting, which is why the control is not called strictness. Edits save immediately, like the book checkboxes above them, and a slider commits once per gesture rather than once per pixel.
- **Two more request protocols: OpenAI Responses and Gemini native.** The **Request protocol** list now has five entries instead of three. **OpenAI Responses** (`POST /responses`) is OpenAI's newer API, and it is not Chat Completions under another path: the body takes `input` rather than `messages`, the system text moves to `instructions`, streaming arrives as typed events (`response.output_text.delta`, `response.reasoning_summary_text.delta`) and the token limit is `max_output_tokens`. It is called statelessly — `store: false` — like every other adapter here, so the conversation stays in CatCup's chat log rather than on the provider's side. **Gemini native** speaks Google's own `models/{model}:streamGenerateContent` with `alt=sse`; the model is in the path, `assistant` turns become `model`, system turns become `systemInstruction`, and thinking parts (`part.thought`) arrive as reasoning. Its key goes in the `x-goog-api-key` header rather than a URL query, so it does not land in a proxy log. A **Google Gemini** service template joins the picker. See `docs/PROVIDERS.md`.

- **The desktop window has its own title bar.** On Windows the native frame is gone and the window buttons are drawn by the app instead — fused rather than added as a strip: they float over the top-right corner of the library rail and the chat header, which reserve 32 px for them, so the brand stays where it already was and nothing gains a row. Dragging anywhere along the top strip moves the window, double-clicking it maximises, and the three buttons minimise, toggle maximise and close, with the glyph flipping to Restore while maximised. The window keeps its resize borders, Aero Snap and its rounded corners. Dragging and the buttons go through the Tauri window API from the page, not through the window procedure: WebView2 covers the client area and takes every mouse message itself, so a hit test over the bar never reaches it — measured, and the reason a subclassed `WM_NCHITTEST` implementation could neither drag the window nor press its buttons. **Hovering the maximise button does not raise the Windows 11 Snap Layout flyout**, because that needs a non-client `HTMAXBUTTON` hit the webview hides; `Win`+arrow and edge snapping still work. `tauri-plugin-decorum` was evaluated and rejected: its snap support simulates `Win+Z` rather than raising the native flyout. See `docs/DESKTOP.md#custom-title-bar`.

- **A long chat can stop forgetting its own beginning.** The rolling summary is a chain — `summary_n = f(summary_{n-1})` — and prompt assembly drops the oldest messages first, so a detail that fell out of the summary _and_ out of the window existed nowhere the model could see. That is now optional to fix. **Keep every summary** (`memory.appendOnly`, off by default) stops re-summarizing: each summary covers a settled range and is final, so the chain stops destroying at the source, and the prompt carries the newest summaries **plus the earliest** — a chat forgets its middle rather than its opening. The stock prompt tells the model to "use that as a base and expand", which is incoherent once nothing is carried, so it is swapped for a version that asks for the new range alone; a prompt you wrote yourself is sent as written.

  Nothing about the chat file changes. SillyTavern already stores one summary per covered message on `extra.memory` and never clears an older anchor — only the read path stopped at the newest, and this setting is what makes it read the list. It is off by default because the other client still injects only the newest, so a chat written this way reads correctly in both but only CatCup uses the extra summaries. The larger fix — indexing the messages themselves so the _middle_ is reachable too — is tracked in #129 and deliberately not in this change; the plan attached to that issue starts with this.

  **The measurement that decides whether that larger fix is worth building** is a command: `pnpm --filter @catcup/server chat-recall <chat.jsonl>`. For each turn it rebuilds the window the prompt would have kept and counts what a BM25 pass would have surfaced from messages the window had already dropped. No provider, no cost. It reports an **upper bound** — a hit scored, which is not the same as a hit being useful — so read a few turns by hand before acting on it.

- **Generation is no longer welded to HTTP.** The code that calls the provider and stores the reply is now a plain async generator (`generateReply`), and the SSE handler is a thin wrapper that relays its events and turns "the browser closed the socket" into a stop. The SSE contract is unchanged — same five events, same abort and partial-reply behaviour — but a second transport can now run the same generation without a `FastifyReply` or a socket, which is what [RFC 0004](docs/RFC/0004-im-integration.md) needs for an IM client. No user-visible change today.

- **A Telegram bot can receive messages, and nothing else yet.** `im/telegram.ts` long-polls the Bot API; a message from the one allowlisted user id reaches a sink, and anything else is dropped **without a reply**, because answering would confirm the bot exists. Polling rather than a webhook is the point: no public address, no TLS, no domain, so an install at home exposes nothing. A failed poll backs off and retries instead of taking the server down, and a `409` says "another process is already polling this bot" rather than "Telegram refused" — the two send a person to different problems.

  The token lives in `data/secrets.json` beside the provider keys and no endpoint returns it; the client sees `hasToken`. **Off by default**, follows the settings across a restart, and stops before the server closes rather than holding the process open for a long-poll timeout. Where a received message goes is the next slice — this one proves a message can arrive and that the allowlist holds.

  Turning it on means message text and replies travel through Telegram's servers. See [SECURITY.md](docs/SECURITY.md): the provider key still never leaves the server, but "local-first" no longer covers the messages themselves.

- **A Telegram chat can become a CatCup chat.** Export the conversation in Telegram Desktop as JSON and choose it in **Import from another app**. The scan shows the participants and how many messages each sent, because the one decision that cannot be automated is **which one is you** — getting it wrong reverses every "I" in the story and is invisible until someone reads the import back. The chat is then written through the same storage path as any other, so it reads back in the app, exports to SillyTavern and distils like a chat made here.

  What it keeps is deliberate. Service rows, joins and messages with no text are **counted and dropped**, not invented into prose. Media becomes a short marker (`[photo]`, `[voice message]`), never a file path — a chat file can be exported or shared, and a path from the exporting machine is a leak. A conversation with more than one other speaker is **refused** rather than flattened into one name, because collapsing two people rewrites who said what. No bot and no token: this reads a file the user already has.

- **The Telegram bot can hold a conversation.** `/chat <character>` binds a Telegram chat to one of their chats — the newest one, because that is the one a person means; `/new` starts a fresh one, `/stop` interrupts a reply, `/who` says what this conversation is bound to, `/help` lists the rest. A plain message talks to the bound character.

  Four decisions worth knowing before using it. **A second message while a reply is being written is refused with a sentence**, not queued — a queue needs its own UI and its own failure modes. **A provider failure answers with a sentence**, because silence looks exactly like a bot that has died. **A chat deleted in the app is reported and unbound**, not recreated, since recreating would fork the story without telling anyone. And **long replies are split on paragraph boundaries, then sentences, then characters** — with CJK punctuation included, because a Chinese reply has no spaces and would otherwise be cut mid-word.

  The binding lives in `im-telegram.json` beside the profile, never in a chat file: it is wiring about which phone reaches which story, and it means nothing to SillyTavern.

- **Tell me when a reply finishes** (`im.notifyOnReply`, off by default). The character's name and the first sentence — not the reply, which is the point. Separate from the bot's own switch, because a bot someone talks to is not necessarily one they want buzzing at them, and a notification is the one part of this feature that carries almost no message content.

- **A chat can be a directed scene.** A per-chat director, off by default, that decides who may speak, keeps the character you play in the prompt without letting the model write them, and offers a short list of options after a reply. Settled by [RFC 0003](docs/RFC/0003-guided-roleplay.md); story mode's graph is reserved but not built, because it needs a plot distillation that has no design yet.

  **It works in a group chat too**, which is the case it was designed for: several characters, one of them yours. A group has no self-play refusal — there is no contradiction between "you are {{char}}" and "never write this member", because the speaker is chosen per turn and a played member is muted for the whole chat — and a played member whose card is temporarily out of the group is accepted rather than blocking the save. The config lives on the group _chat_ rather than the group, so two chats with the same cast can be two different stories.

  There is no form for any of it yet: the director is API-only, and `LIMITATIONS.md` says so.

  **A single chat refuses to play its own card** — a `400` that names both ways out (a group chat, or a narrator card with the cast played from the world book). The card block tells the model "you are {{char}}", so a chat that both speaks as its character and forbids writing them contradicts itself, and the failure would show up as a model that occasionally writes the person's lines.

  **Choices are a line-oriented sentinel block, not JSON**, and that is the reliability plan rather than a detail: a streamed JSON object has to balance its brackets and survive an unescaped quote, while a line format degrades — a block cut off mid-way still yields the lines before the cut, and no block means no options rather than a failure. The block is stripped before regex scripts run, so a stored chat never contains the sentinels, and clicking an option sends its label through the ordinary send path. **Choices can never fail a reply.**

  A chat with no `director` key produces the same prompt and the same file it always did, which is the compatibility promise this rests on.

### Changed

- The README leads with what the product is and the Windows download, before the install notes, and
  merges its duplicated "why another tavern" and "compatibility" prose into one bullet list plus one
  table; the desktop features that shipped in 0.3.1 are no longer marked **next**, the provider entry
  names all five request protocols, and a License section states the AGPL position and points at
  `NOTICE`.

- **Compatibility is stated as two rules rather than one.** Data formats stay a hard constraint — every file CatCup writes must remain readable by SillyTavern, with field names, the JSONL header shape and unknown-field preservation intact. Runtime semantics are now a default rather than a mandate: a divergence is allowed when it is opt-in, leaves imported data readable by both clients, and is recorded in `docs/ST-COMPATIBILITY.md` with the reason and the setting that controls it. `CLAUDE.md`, `docs/ST-COMPATIBILITY.md` and `docs/LIMITATIONS.md` follow.
- CatCup-only derived state — indexes, embeddings, caches — lives in a sidecar beside its source, and anything that must be written into a SillyTavern object goes under `extensions.catcup`, which SillyTavern preserves and ignores.
- `GET /api/auth/status` answers `desktop` and `titleBar`, so the page can tell the shell from a browser tab and draw the bar only where the frame was removed. The geometry is passed in from the shell as `CATCUP_TITLE_BAR_*` rather than duplicated in the SPA.

### Fixed

- **Enabling or disabling a world info book no longer resets the other scan settings.** The book checkbox sent a patch carrying only `globalBooks`, but the request schema applied every other field's default to that patch on the way in, so the merge in storage overwrote the saved depth, budget percentage, budget cap, recursion, minimum activations and the matching flags with their defaults. `PATCH /api/settings` now treats `worldInfo` as a true partial, the same way it already treated `memory`. Nothing on disk changes shape; a saved value simply survives the next book toggle.

## 0.3.2 — 2026-11-16

### Added

- **Add provider** opens a picker whose first entry is **Custom provider** — "choose its protocol, enter the request URL and API key yourself" — with the four service templates below it under **Or start from a service**. The custom entry starts with an empty base URL, so the endpoint is typed rather than inherited from a vendor, and the templates stay one-click prefills of name, kind and default URL.
- The provider form asks for a **request protocol** instead of a vendor. `openai`, `openrouter` and `custom` are one protocol — OpenAI Chat Completions — with different defaults, and the label now says so: **OpenAI Chat Completions** (`/chat/completions`, SSE), **Anthropic Messages** (`/messages`, SSE) and **Ollama native** (`/api/chat`, NDJSON), each with a line naming what it covers. Changing the protocol keeps a hand-typed base URL, and a provider still matching its template keeps that template's kind when the protocol it speaks is chosen again. The stored `kind` values are unchanged, so no provider needs a migration. New exports in the shared schema: `PROTOCOL_LABELS`, `PROTOCOL_HINTS`, `PROVIDER_PROTOCOLS`, `protocolFor`, `PROVIDER_TEMPLATES`, `providerInitials`, `providerSummary`, `expectsKey`.
- Every dropdown in the app is now a CatCup control rather than the operating system's. A native `<select>` and a `<datalist>` draw their own popup, which on Windows arrived as a white system list in the middle of the dark panel and could not be styled. **`Select`** replaces the select: the same `.input-shell` trigger, a portalled `role="listbox"` in `surface` with `line` borders, an amber mark on the selected row, arrow keys, Home/End, type-ahead, Escape that closes the list without closing the dialog under it, and three sizes (`md` form field, `sm` compact row, `xs` header chip). **`Combobox`** replaces the datalist: a free-text field with filtered suggestions that still accepts a value the list does not carry, for model ids, TTS voices, image samplers and bulk tags. Both are documented in `docs/DESIGN.md`.
- A checked-in Claude Code skill, `novel-to-catcup`, that turns a novel or any long text into a pack CatCup imports as-is: one V2 character card per character, one ST-shaped world info book, persona text for a character the user wants to play, and portrait prompts for every card. It carries a pack validator and an offline PNG card writer that stamps `chara`/`ccv3` metadata into a chosen portrait, plus a script that compares its output with the server's own writer. This is the static, script-backed variant for people working in a checkout; it is distinct from the generated, prompt-only export served at `GET /api/distill/skill`, which carries no scripts. See `docs/DEVELOPMENT.md#skills`.
- **The distillation pipeline can leave the app.** **Distil somewhere else → Skill** in the book dialog — and `GET /api/distill/skill` — downloads a Claude Skill as a ZIP: the four stages, every prompt verbatim, the JSON Schema for the analysis reply and the draft rows, and a description of SillyTavern's world info and Character Card V2 shapes. It is prompt-only and generated from the same constants a run sends, so a prompt edit changes both the server and the export; a test fails if a bundle ever carries a prompt the runtime no longer uses. It needs no provider, model or uploaded book, and carries no book text, key or secret.
- **Play as this character.** A button in the character library copies a card into a persona — `description`, `personality`, `scenario` and example messages — so you can speak as someone from your cast instead of retyping them. The card's opening line is deliberately left behind: that is the assistant's line, and a persona carrying it makes the model greet itself. The persona is a copy, so editing it never touches the card.
- **A persona can carry a card's voice.** `personality`, `scenario` and `mesExample` join `name` and `description` as optional fields. In the prompt the first three are joined into the one persona slot as labelled paragraphs, and the examples are parsed as **your** turns — never the assistant's. All three default to absent, so an existing `settings.json` produces exactly the prompt it always did, and the persona editor shows them behind a disclosure.
- **Generate a portrait from a card.** **Portrait** in the character editor drafts an image prompt from the card's description and personality — no chat involved, so it works for a card that has never been spoken to — and **Use as portrait** makes the result the character's picture. A PNG card is rewritten with the same data embedded; a JSON card becomes a PNG card, because a card's picture and its data are one file. The previous picture is not kept, and the confirmation says so. The instruction is editable as **Portrait instruction** in Settings → Images.
- **Drafting an image prompt no longer needs an image backend.** Drafting is a chat-model call, so **Draft from chat** and **Draft from card** work with image generation disabled, and a **Copy** button puts the prompt wherever you want it. Only generating and setting a portrait need a backend.

### Changed

- A provider row in the library footer and the Providers list names its service and default model through one helper, so a custom provider reads as its protocol rather than as a vendor it does not have.
- Interface copy names what the app does rather than the client its formats came from. The import entry is now **Import from another app**, its dialog asks for a data folder, and its error, the About tab, the Settings, Memory, Quick Replies and Regex hints, the empty group editor, the Quick Replies format check and the `index.html` / `package.json` descriptions no longer name SillyTavern. Attribution stays where it must: `NOTICE`, `docs/REUSE.md`, the per-file `Derived from` headers and the compatibility pages are unchanged, and the data-format and API pages still describe the formats in the ecosystem's terms.

### Fixed

- **0.3.2 is offered as an automatic update.** The signing key in the repository secrets held no key, so 0.3.0 and 0.3.1 both shipped without updater artifacts and could not update themselves. Two faults had to be fixed: a keypair is deployed, with the private key in the secret and the matching public key pinned in `tauri.conf.json`; and the publish step only looked for a legacy `*.nsis.zip`, while the current bundler signs the installer itself and leaves `<installer>.exe.sig`, so the signature, and the `latest.json` an installed app polls, were never uploaded even once signing worked. The release workflow now accepts either shape, logs the key's length so an empty secret is visible before a 30-minute build, and warns on a zero. `docs/DESKTOP.md` records how each failure stays silent.
- **The desktop app opened a console window at startup.** The bundled `catcup-node` is a console-subsystem executable, and Windows allocates a console window for one started by a GUI process; it stayed on screen until Quit. The shell now passes `CREATE_NO_WINDOW` on Windows, so the child gets a hidden console and nothing is drawn. Its stderr used to be inherited from a console that did not exist, so server errors were lost: both streams now append to `shell.log` in the data directory, rotated to `shell.log.1` at launch past 4 MB, which is where to look when the installed app will not start.
- **The Add button beside the model field closed the Providers panel.** The panel is one form, and the row that adds a model id was a second `<form>` nested inside it — invalid HTML, whose submit reached the panel's save handler and could run a native submission that reloaded the app. The row is a `div` now, with a `type="button"` Add and an Enter handler; it adds the id and touches nothing else. `docs/DESIGN.md` records the rule.
- **Sign out was offered when no password was set.** An open desktop session has nothing to end, and the action led to a login screen that could only answer "Setup required". The library footer hides it there, `POST /api/auth/logout` answers `409 NO_PASSWORD` for that install so a stale tab cannot reach the dead end, and the client refetches the real status instead of writing a guessed one into its cache.
- A portrait has to be a PNG, and the API says so (`IMAGE_PORTRAIT_FORMAT`) rather than accepting a JPEG or WebP that cannot hold the card data.

## 0.3.1 — 2026-11-15

### Added

- A **book** can be uploaded to be distilled into a world info book and character cards ([RFC 0002](docs/RFC/0002-book-distillation.md)). `.txt`, `.md` and `.epub` are read into chapters, and the result is stored in the profile that uploaded it so a run can be repeated with a better model. The text is decoded as strict UTF-8 first, then GB18030, so a Chinese novel saved as GBK reads correctly instead of arriving as mojibake. An EPUB is read in spine order; font obfuscation is not DRM and is accepted, while a spine document that is itself encrypted is refused by name.
- **Distil from a book** turns a book into lore. **Sections only** writes one world info entry per chapter straight from the text, with no model call, and finishes in a second. **Model draft** reads every chapter, merges what it found and writes each recurring character up as a card: one request per chunk, one per entity mentioned twice or more, and one batched request to settle near-identical names — a passing mention is summarised from the merge without a request, marked low confidence and left unticked. A chapter whose reply cannot be read is retried once and then reported as skipped, never failing the run.
- Nothing reaches your library until you accept the review sheet, where every row can be ticked, edited in place and merged into another. Accepted output is an ordinary world info book and ordinary V2 cards, written to this profile or to the shared scope.
- A distillation run is server-side and is deliberately **not** tied to the dialog: a long book keeps running when the tab closes, and **Reattach to a running book** picks it back up. Switching profiles is refused while a run is in flight, because a run resolves its scope when it starts.
- `data/profiles/<id>/books/` holds the uploaded file and a record of its section titles and sizes — never the text, which is re-parsed from the source on demand. `POST /api/distill/books` returns the sections and an estimate of how many requests a run would cost, from the same tokenizer the prompt budget uses.

- A **profile** is a data scope. Characters, chats, groups, world info, presets, quick reply sets, regex rules, personas, generated images and every setting belong to one profile, so a novel campaign and a mystery campaign can each hold a character called `Mira` without colliding. Only the provider list, its models, the API keys and auth are shared, because re-entering one endpoint and its key per campaign buys nothing. A profile pins its active provider and a preferred model.
- A `data/` folder from an earlier version migrates into `profiles/default/` on first start, keeping the old `settings.json` as `settings.json.v1-backup` and writing one line per step to `migration.log`. The move is a rename within one volume and rolls back if any step fails; `CATCUP_MIGRATE_DRY_RUN=1` prints the plan without touching anything.
- The library footer shows the active profile above the active provider. Choosing another profile switches the whole workspace — its cast, chats, lorebooks, presets and settings — and the selection is cleared because every id belonged to the old one.
- Profiles can be switched from **Settings → Profiles**: create one empty or copy another profile's configuration, rename it, make it active, archive it and restore it. A switch is refused while a reply is streaming, because a generation resolves its provider and preset when it starts and must not write into another profile's chat.
- A library item can be marked **reusable in every profile**. Characters, world info books, presets, quick reply sets, regex rules and personas each move into `data/shared/` and every profile sees them; the folder stays empty until something is marked. - An "Import from SillyTavern" entry in the character library that drives that endpoint.
- Windows desktop app: a per-user NSIS installer that bundles its own Node runtime, a single-file server build and the SPA. It starts the server on an OS-chosen port, opens it in a window, and stops the server when the window closes.
- The desktop app is single-instance — a second launch focuses the open window — and puts the server in a job object, so killing the shell also kills the server.
- `CATCUP_BUNDLE_DEPS=1` builds the server with every dependency inlined, which is what the desktop bundle ships.

### Changed

- Pretty log output is now used only when stdout is a terminal. A packaged build pipes stdout into the desktop shell, where `pino-pretty` is not installed.

### Changed

- Settings replace `persona` with `personas` and `activePersonaId`. `PATCH /api/settings` accepts the new fields; sending `persona` is now a validation error.

### Fixed

- World info entries are no longer dropped when `sticky`, `cooldown`, `delay`, `group`, `groupWeight`, `triggers` or a key list is `null`, which is what the SillyTavern editor and several card exporters write.
- An entry with no `selective` field now defaults to `true`, as SillyTavern's entry template does, so an entry that only lists secondary keys applies their logic.
- An explicit `order: null` now reads as `0`; before, it shared the missing-field default of `100` and sorted lorebook entries differently from SillyTavern.

### Changed

- Prompt assembly replaces the M0 builder's single labelled character sheet with one message per marker, in prompt-order order.
